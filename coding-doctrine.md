When working on firmware, ELF binaries, or vulnerability analysis:

- Attachments are virtual paths, not disk files. A user-supplied firmware or ELF arrives as `session-file://<seq>/<n>` and its bytes live in the session log, not on the filesystem. Before any shell/ELF work: call `read session-file://list` to enumerate attachments, then `diot_export_attachment` to write the bytes to a real path (it returns the saved absolute path), then use that real path everywhere. Never `Expand-Archive` or open a `session-file://` reference directly in shell — it does not exist on disk. If the exported directory is empty or the file is missing, verify the export path and list it before searching the host's private app-data folders.
- Prefer the project Python over bare `python`. For analysis scripts use the absolute venv interpreter (e.g. `D:/AgentLearning/IOT Agent/LIVA/.venv/Scripts/python.exe`) unless a tool already wraps it; a bare `python` may be a different, broken runtime and every failed shell round-trip wastes an approval.
- Pick the analysis target with evidence, not habit. A firmware image contains many ELF files; the web-facing services (httpd, cgibin, upnpd, lld2d, miputil, and similar) carry nearly all reachable attack surface. When a user hands you a firmware image, inventory it first, list the candidate ELF files, and choose the one with real entry points (CGI handlers, network listeners, input parsers). If the evidence points at another ELF, switch and say why. History shows the historical CVE sinks concentrate in a small set of binaries (e.g. cgibin), so a wrong first guess is normal — re-target rather than forcing the analysis.
- Cross-ELF flow is a first-class path. A source in one ELF (httpd parsing a query string) that reaches a sink in another (cgibin calling `system`) is one finding, not two. When a service hands input to another over CGI, IPC, or shared state, follow the data across the boundary. Build the parent-child call relation across binaries before declaring a path dead.
- Resolve indirect calls before declaring a sink unreachable. MIPS `jalr $t9`, GOT/PLT slots, and function-pointer tables hide the real callee. Use decompiler output (IDA decompile listings, call graphs) to resolve them; a call graph that is obviously smaller than the symbol table (e.g. 88 vs 277 functions) means resolution failed, not that the functions are unreachable.
- Read the file before editing it. Never guess a path, an import name, or an API shape.
- Create generated files, including Markdown and HTML, in the current workspace by default. Use paths relative to the cwd in the latest runtime context, such as `result.md` or `result.html`. A leading `/` is an absolute operating-system path, not a workspace prefix. Use a different destination only when the user explicitly requests it.
- Change one thing at a time and verify it before moving on. Prefer the smallest edit that works.
- Build large generated files, including HTML and SVG, across multiple tool calls. Write a small valid scaffold with unique section markers first, then replace one marker per edit call with a complete section. Aim for at most 8 KiB of new content per call, and retain a unique marker for each remaining section. Never attempt the entire large file in one tool call.
- Run the project's own test or build command to check your work. If none exists, say so instead of inventing one.
- Keep output short. Report what changed, what you verified, and what is still open.
- Leave the workspace consistent: no half-applied edits, no stray files.
